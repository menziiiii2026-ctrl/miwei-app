# App 接入与模型协作方案

## 固定装饰层编译

模板编译器必须按每份 manifest 的 `layer_stack` 渲染 `fixed_decoration_layers`，坐标单位为相应 `reference_canvas_px` 的 px。`asset_ref` 由 App 打包或映射，`drawable` 直接绘制；`subject_clip_window` 同时保存裁切窗与主体变换。AI 仅可输出背景、氛围、文案与模板候选，不能输出装饰层开关、素材选择或坐标。详见 [固定装饰层协议与审计](固定装饰层协议与审计.md)。

## 结论

可以统一，而且不应把模板能力绑定到 Codex 深图或任意一个模型。正确的产品边界是：**模型负责理解与选择；模板引擎负责布局；画布负责编辑；渲染器负责出图。**

最终交付物的源文件不是图片，而是一份 `canvas-scene.v1` 场景 JSON。导出的 3:4 PNG/JPG 只是该场景的预览或分享副产品。

这会让 Codex、其他多模态模型、规则引擎，甚至无 AI 的用户手动选模板，都生成同一种分层画布。

## 当前统一后的模板目录

运行时唯一目录为 [`../app-contract/template-catalog.v1.json`](../app-contract/template-catalog.v1.json)。它收录当前保留的 14 个模板：

| 餐品数量 | 可调用模板 | 备注 |
|---:|---|---|
| 1 | `1_模板1`、`1_模板2`、`1_模板3` | 画框、暗背景描边、局部暗层。 |
| 2 | `2_模板1`、`2_模板2` | 日记拼贴、线圈本。 |
| 3 | `3_模板1`、`3_模板2`、`3_模板3` | 矩形裁切、时间戳、暗层三角。 |
| 4 | `4_模板1`、`4_模板2` | S 路径、括号中段裁切。 |
| 5 | `5_模板1`、`5_模板2`，可备选 `6_模板2` | 折角双列、括号中段；拍立得轨迹可伸缩支持 5–7。 |
| 6 | `6_模板1`、`6_模板2` | 拍立得环绕、递增拍立得轨迹。 |

每个目录下旧的 `manifest.json` 保留为视觉配方和固定资产索引；App 不直接依赖不同格式的旧字段，而是只读取统一目录并由模板编译器适配。**`template-catalog.v1.json` 是 App 的运行时真相来源。**

## 不可妥协的图层协议

所有模板最终必须编译成 [`../app-contract/canvas-scene.schema.v1.json`](../app-contract/canvas-scene.schema.v1.json) 允许的独立层。坐标一律使用 `0–1` 相对值，最终尺寸可以是任意像素，但比例固定 `3:4`。

| 图层 `kind` | 内容 | 是否可编辑 |
|---|---|---|
| `background` | 背景库照片或单独生成的背景资产 | 替换；不能和主体融合。 |
| `mask` | 黑色半透明遮罩、局部暗层 | 移动、缩放、删除、改透明度。 |
| `board` | Today 画框、线圈本、拍立得、记事本等固定画板 | 移动、缩放、删除；从贴纸库引用。 |
| `subject` | 用户上传的透明餐盘 PNG | 替换、移动、缩放、旋转；可按模板裁切。 |
| `outline` | 可移除的白描边、黄色描边、括号等 | 删除、改颜色和粗细；绝不能烘焙到主体图中。 |
| `sticker` | SVG/PNG 固定贴纸，如星星、箭头、圆贴纸、星芒 | 移动、缩放、删除、随机替换。 |
| `text` | 菜品名、日期、短句等 | 文本、字体、颜色、位置均可编辑。 |

固定装饰应引用 `asset_ref`，例如 `six-item-polaroid-ring/polaroid-square-01`；不要让模型重新生成这些元素。用户食物、背景、描边、贴纸和文字必须永远是独立节点。

### 裁切窗口与内容变换

带裁切的主体必须同时保存 `clip_frame` 和 `content_transform`。前者表示画布上可见窗口的位置与尺寸；后者表示原图在窗口内的缩放与水平/垂直偏移。用户调整裁切后，这两类数据必须一起持久化，以便重新打开时精确恢复。

### 组合容器

拍立得、相框等多层结构使用 `groups` 与图层的 `group_id` 建立组合：

- 首次点击选中整组，整组移动、缩放、旋转和调整层级。
- 再次点击或双击子元素进入组内编辑；食物可替换，并可调整在框内的位置和缩放。
- 点击画布空白处退出组内编辑。
- `locked_structure` 为真时，用户不能拆散或破坏模板必需结构；子层仍可根据各自 `editable` 权限被替换或调整。

## App 的生成管线

```text
上传餐盘 PNG + 菜品数据 + 可选背景
              ↓
输入分析（模型或规则）：数量、菜名、色调、可用背景
              ↓
模板路由器：按数量筛选 catalog，再按适配度排序
              ↓
模型输出 Composition Intent（受 JSON Schema 约束）
              ↓
校验与回退：只保留允许的模板、背景、颜色、文字长度
              ↓
模板编译器：Intent + Recipe + Asset Library → canvas-scene.v1
              ↓
可编辑画布（逐层显示） → 预览渲染器 → 导出 3:4 图片
```

### 1. 输入分析

输入数据建议固定为：

```json
{
  "foods": [
    {"id": "food-01", "cutout_asset": "upload://food-01.png", "dish_name": "照烧鸡排饭"}
  ],
  "background_candidates": [
    {"id": "bg-tableware-01", "asset": "library://bg-tableware-01", "tags": ["餐具", "暖色"]}
  ],
  "date": "2026-09-14",
  "period": "today",
  "locale": "zh-CN"
}
```

App 在本地或后端确定 `foods.length`，绝不能信任模型自行猜测数量。上传主体应预先完成抠图；当前产品输入就是透明圆盘 PNG，可直接作为 `subject` 层。

`period` 只能由 App 入口确定：今日为 `today`，本周为 `week`。两个入口共用同一套模板和编辑器，不设模板偏好，只按菜品数量路由。`1_模板1` 的顶部周期文字由 App 编译：`today` 显示 `Today`，`week` 显示 `This Week`；该文字不得烘焙在画板 SVG 中，也不由 AI 猜测。

### 2. 模型的受限职责

任一模型只返回 [`../app-contract/composition-intent.schema.v1.json`](../app-contract/composition-intent.schema.v1.json) 定义的 `composition-intent.v1`：

- 在该数量允许的模板中给出最多 3 个排序候选；
- 从 App 给它的背景候选 ID 中选一个；
- 给出 1–5 个情绪标签、一个强调色和短文案；
- 可解释自己的选择，但**不输出像素、不输出 SVG、不输出图层坐标、不生成餐盘图**。

因此模型可替换。Codex 深图可做输入分析；换成 GPT、Claude、Gemini 或本地视觉模型时，只需各写一个 `ModelAdapter`，把该模型的结果转换并验证为同一份 Intent JSON。

### 3. 路由与回退

模板路由器必须是确定性的：

1. 先用 `food_count` 查目录，得到白名单。
2. 删除不满足背景条件的模板（例如 `6_模板2` 必须有路灯背景）。
3. 接收模型给出的排序，但只接受白名单中的第一个有效模板。
4. 模型不可用、输出不合法或置信度低时，使用每个数量的首个默认模板，仍可生成完整画布。

示例：6 道菜、可用餐具背景、没有路灯背景时，路由器应只保留 `6_模板1`；模型不能擅自选择 `6_模板2`。

### 4. 模板编译器，而不是模型出图

模板编译器读取模板坐标、裁切规则、固定资产、[`template-text-layouts.v1.json`](../app-contract/template-text-layouts.v1.json) 中由 manifest `text_layout_ref` 指向的文本布局，以及可编辑性，生成一份完整 `canvas-scene.v1`：

- `subject` 数量必须等于餐盘数量；
- 模板要求的每个 `board`、`mask`、`outline`、`sticker` 都生成独立节点；若 manifest 含 `fixed_decoration_layers`，模板编译器必须以其 `reference_canvas_px` 的 `frame_px` 归一化坐标、`z_index`、颜色绑定及编辑权限为唯一来源，不能从参考图或 Swift 常量推导；
- 所有文本均为 `text` 层，菜品名绑定 `dish_name`，不在图片里绘制文字；文本的 frame、字体、字号、行高、对齐和旋转从文本布局契约读取并归一化，AI 与 Swift 都不提供坐标；
- 背景先匹配，再放遮罩；不能用从背景取色的纯色假装真实背景；
- 在导出前执行越界、主体重叠、层级顺序、可读性和 3:4 校验。

Figma 在这里的角色是视觉验收工具，不是 App 的运行时依赖。App 可以用任意支持对象图层的画布实现；只要能读写 `canvas-scene.v1`，更换画布技术或模型都不影响模板数据。

## 模型适配层接口

```ts
type ModelAdapter = {
  analyze(input: CompositionInput): Promise<CompositionIntent>;
};

type TemplateCompiler = {
  compile(input: CompositionInput, intent: CompositionIntent): CanvasScene;
};
```

模型适配层的输出必须经过 JSON Schema 校验；模板编译器再做业务校验。任何一层失败都不得返回扁平图片，而应返回默认模板编译出的可编辑场景或明确错误。

## 最小可落地顺序

1. App 先实现 `canvas-scene.v1` 的读写、图层面板、移动/缩放/删除、文本编辑和 3:4 导出。
2. 接入固定贴纸库与统一模板目录；先支持不需要模型的“按数量手动选模板”。
3. 编写模板编译器，将 14 个模板逐一输出场景 JSON。
4. 最后接一个模型适配器做自动模板推荐、背景筛选和短文案；失败时回退到确定性模板选择。

## 今日 / 本周自动更新规则

- 菜品新增或变更后，后端将对应作品标记为需要更新；该标记不在前端显示。
- 从最后一次菜品变更起重新计时。连续 5 分钟没有新菜品时，自动生成或更新作品。
- 若 5 分钟内再次新增菜品，取消原计时并从最后一次变更重新计时。
- 更新成功后覆盖该时间范围的旧作品，不对用户展示多个自动版本。
- 模板路由和本地合成可重用已有结果；只在确有必要时重新请求 AI 文案或适配度排序，避免无效算力与服务成本。

这样第一版 App 即使暂时没有 AI，也能稳定生成和编辑；AI 只提升“选哪个模板、配什么背景、写什么短句”的质量，而不会破坏画布可编辑性。
